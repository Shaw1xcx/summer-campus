TOPIC 01 · REPRESENTATION

编码、压缩与序列化

比较同一份逻辑数据在 CSV 和 Parquet 中的类型信息、存储空间与读写成本。

学习目标理解序列化是将内存中的数据结构转换为可存储形式的过程；能解释为什么 Parquet 不等同于“压缩过的 CSV”。
直观例子：CSV 像把表格逐行抄成文字：数字 1178 会保存为四个字符。Parquet 则知道这一列是整数，会按整数列组织，再进行编码和压缩。因此 Parquet 不只是“把 CSV 压缩一下”。

这种表示方式有什么好处

Parquet 的价值来自“保留类型 + 按列组织 + 编码压缩 + 元数据”，不是只把文件后缀换掉。

少读无关列

查询只需要 symbol 和 Volume 时，可以不读取 Price、Time 等列；CSV 通常仍要解析每一行。

减少磁盘与网络字节

同类型值连续排列，更容易使用字典、RLE、Delta 和 ZSTD 等方法缩小数据；读取和传输的字节也随之减少。

避免反复猜类型

整数、字符串和 Schema 被写入文件。读取器不必每次从文本重新判断类型，也更容易发现字段不一致。

查询前还能继续排除

Footer 和行组统计可记录最小值、最大值等信息；条件不可能命中的行组可以直接跳过。

代价与适用边界：Parquet 不适合人工直接编辑，写入逻辑比 CSV 复杂；只有几行数据或主要用于跨系统文本交换时，CSV 仍可能更直接。

Parquet 本身是什么

Apache Parquet 是一种用于保存表格数据的列式二进制文件格式。它和 CSV、Excel 文件一样，是“数据如何写进文件”的规格；它不是 Python 库、不是数据库服务，也不会自己执行查询。Polars、DuckDB、Pandas 和 Spark 都可以读写 Parquet。

列式存储

同一列的值放在一起。查询只需 symbol、Price 时，引擎可以不读其他列。

保留类型与 Schema

文件会记住某列是整数、浮点数还是字符串，读取时不必像 CSV 那样从文字重新猜测。

适合分析型读取

常见分析只读少数列，却要扫描很多行。Parquet 的列组织方式就是为这类工作负载设计的。

不适合频繁修改单行

Parquet 更像“按批发布的分析文件”。如果要频繁插入、更新某一行，通常由数据库负责。

一句话区分：Parquet 负责“怎么存”；Polars 和 DuckDB 负责“怎么读和算”；ZSTD 或 Snappy 负责“字节怎么压缩”。

from pathlib import Path
from time import perf_counter
import gzip
import io
import polars as pl

source = Path("data/trades.csv")
df = pl.read_csv(source)
out = Path("data/format-benchmark")
out.mkdir(parents=True, exist_ok=True)

# 统一计时函数：既返回函数结果，也返回实际经过的秒数。
def timed(callable_):
    start = perf_counter()
    value = callable_()
    return value, perf_counter() - start

# CSV.gz 仍然是文本 CSV，只是在文件外层增加 gzip 压缩。
def write_gzip(path):
    with gzip.open(path, "wb", compresslevel=6) as stream:
        stream.write(df.write_csv().encode("utf-8"))

# 五种输出使用不同文件名，防止互相覆盖。
files = {
    "CSV": out / "trades.csv",
    "CSV.gz": out / "trades.csv.gz",
    "Parquet-ZSTD": out / "trades_zstd.parquet",
    "Parquet-Snappy": out / "trades_snappy.parquet",
    "Parquet-LZ4_RAW": out / "trades_lz4.parquet",
}

# 每种格式分别定义写入和读取动作，便于使用同一套计时逻辑。
writers = {
    "CSV": lambda: df.write_csv(files["CSV"]),
    "CSV.gz": lambda: write_gzip(files["CSV.gz"]),
    "Parquet-ZSTD": lambda: df.write_parquet(files["Parquet-ZSTD"], compression="zstd"),
    "Parquet-Snappy": lambda: df.write_parquet(files["Parquet-Snappy"], compression="snappy"),
    # Polars 参数名为 "lz4"，写入的是 Parquet 支持的 LZ4_RAW codec。
    "Parquet-LZ4_RAW": lambda: df.write_parquet(files["Parquet-LZ4_RAW"], compression="lz4"),
}
readers = {
    "CSV": lambda: pl.read_csv(files["CSV"]),
    "CSV.gz": lambda: pl.read_csv(io.BytesIO(gzip.decompress(files["CSV.gz"].read_bytes()))),
    "Parquet-ZSTD": lambda: pl.read_parquet(files["Parquet-ZSTD"]),
    "Parquet-Snappy": lambda: pl.read_parquet(files["Parquet-Snappy"]),
    "Parquet-LZ4_RAW": lambda: pl.read_parquet(files["Parquet-LZ4_RAW"]),
}

# 每次演示都重新写入、重新读取，并检查读取行数是否一致。
rows = []
for name in files:
    _, write_seconds = timed(writers[name])
    loaded, read_seconds = timed(readers[name])
    assert loaded.height == df.height
    rows.append({
        "format": name,
        "size_KiB": round(files[name].stat().st_size / 1024, 1),
        "write_ms": round(write_seconds * 1000, 2),
        "read_ms": round(read_seconds * 1000, 2),
    })

# 按文件大小排序，再讨论“更小”和“更快”是否为同一件事。
print(pl.DataFrame(rows).sort("size_KiB"))

TOPIC 02 · LAYOUT

Parquet 数据怎样拆成多个文件

同样的 12,000 行数据，换一种文件摆法，查询时需要打开的文件就可能完全不同。

看完本节应当能回答“数据布局”到底在摆什么；为什么按日期存储适合查某一天；为什么分得越细不一定越快；“分区剪枝”和 Parquet 文件内部的筛选有什么区别。
先记住一句话：Parquet 规定“一个文件内部怎样存”；数据布局决定“一整张表拆成几个文件，以及每个文件装哪些行”。本节只改变文件的装法，表中的数值一行也不改。

合理的数据布局有什么好处

布局不会改变答案，它改变的是查询为了得到答案必须接触多少文件和多少数据。

查询前跳过整批文件

按日期布局后，查 20260630 可以先排除另外 5 天；不必打开文件后才发现日期不符。

独立文件可以并行

多个日期文件可以分配给不同线程或工作进程读取；单个超大文件往往提供更少的任务拆分机会。

便于分批更新和保留

新增一天可以追加一个日期分区；删除过期日期也可以按目录处理，而不必重写整张历史表。

代价与适用边界：分区键必须匹配常见查询。分得过细会产生小文件，固定的打开、元数据和调度成本可能抵消剪枝收益。

先把这份自编数据数清楚

data/trades.parquet 中有 6 个日期、8 只虚构股票；每个“日期 × 股票”组合有 250 行。因此总行数是：

6 个日期×8 只股票×每组 250 行=12,000 行

这 12,000 行可以有许多种装法。下面四种装法的内容完全相同，区别只在于文件的数量和每个文件所覆盖的范围。

一个文件装 12,000 行，里面混合 6 天和 8 只股票。

B · 按日期拆6 个文件

每个日期一个文件；每个文件装 8 × 250 = 2,000 行。

C · 按股票拆8 个文件

每只股票一个文件；每个文件装 6 × 250 = 1,500 行。

D · 日期 × 股票48 个文件

每个日期、每只股票一个文件；共 6 × 8 = 48 个，每个 250 行。图标只画一半，数量以 48 为准。

“布局”就是上面这项选择。它不等于排序，也不等于压缩。布局回答的是：哪些行被放进同一个文件，以及查询前能否只凭文件路径排除其他文件。

TOPIC 03 · POLARS

Polars Lazy API：从查询计划到执行

懒执行先构建完整查询图，再由优化器调整过滤、列选择和聚合的执行位置。

学习目标能说明 scan_* 与 read_* 的执行时机差异；能使用 explain() 检查过滤和列选择是否被移到扫描阶段。
直观例子：要从仓库取“成交量大于 100 的股票代码、价格和成交量”时，Eager 做法像先把整座仓库搬进房间再挑选；Lazy 做法先看完整清单，只从仓库取需要的三列和符合条件的记录。

Polars Lazy 有什么好处

Lazy 模式先收集完整计算计划，再决定怎样执行；因此优化器能看到步骤之间的关系。

过滤尽量靠近数据源

谓词下推可让不符合条件的行尽早消失，减少后续分组、连接和排序的工作量。

只读取最终需要的列

投影下推可以把选列移入扫描阶段，减少 Parquet 读取量和中间 DataFrame 的内存占用。

整条流水线一起优化

优化器可以合并表达式、安排并行执行并避免部分无用中间结果，而不是逐行解释 Python 循环。

计划可以检查

explain() 会显示过滤和选列落在什么位置，使“是否真的下推”成为可核对的事实。

代价与适用边界：真正的错误可能到 collect() 才出现，调试比逐步执行更间接；很小的内存表不一定能看到明显性能差距。

Polars 本身是什么

Polars 是一个用于读取、整理、转换和分析表格数据的 DataFrame 库。它的 Python API 用法与 Pandas 有相似之处，但核心主要由 Rust 实现，并将列式表达式、多线程执行和查询优化作为重要设计。

DataFrame 是什么

它是内存中的二维表：有列名、行和每列的数据类型。可以过滤、选列、分组、聚合和连接。

Polars 不是文件格式

.parquet 是磁盘上的文件；Polars 是打开文件并执行计算的程序库。它也能读 CSV、JSON 等格式。

Expression 表达式

pl.col("Volume") >= 100 不是一个单独数值，而是对整列要执行什么操作的可组合描述。

Eager 与 Lazy 两套入口

read_* 直接得到 DataFrame；scan_* 先得到 LazyFrame 查询计划，到 collect() 才运行。

名称它在本讲义中的角色它不是什么
Parquet保存表格数据的列式文件格式不是计算引擎
Polars用 Python API 组织 DataFrame 处理管道不是文件或数据库服务
DuckDB用 SQL 查询 Parquet 和其他表格数据不要求把本地 Parquet 先导入服务器

Lazy 不是“慢慢运行”，而是“先不运行”

read_parquet() 的意思是“现在把数据读成 DataFrame”；scan_parquet() 的意思是“先记下数据在哪里，稍后再决定怎么读”。Lazy 在这里指“延迟执行”，不是性能慢。

代码当下发生什么数据是否已读入
pl.scan_parquet(path)创建“从 Parquet 读数据”的计划节点。没有
.filter(...)在计划上加一个过滤节点。没有
.group_by(...).agg(...)记下分组和聚合的要求。没有
.explain()让你看优化后准备怎么做。通常不执行业务查询
.collect()优化完整计划，真正读取、过滤、聚合并返回 DataFrame。是
谓词下推（Predicate Pushdown）

把 Volume >= 100 尽量移到读文件时执行。越早丢掉无关行，后面聚合的数据越少。

投影下推（Projection Pushdown）

“投影”在数据库里指选列。查询只用 symbol、Price、Volume，就不读其他列。

怎么知道优化真的发生了？ 不要只看耗时。本页真实计划中的 PROJECT 3/5 COLUMNS 证明只读 5 列中的 3 列；SELECTION: Volume >= 100 证明过滤已靠近扫描节点。
知识讲解：为什么“先看到全部计划”才能优化eager vs lazy · predicate pushdown · projection pushdown
1. Eager（急切执行）

每步 API 调用立即生成结果。如果第一步已把全部列和全部行读入内存，后面的过滤无法挽回已发生的 I/O 与解析成本。

2. Lazy（懒执行）

scan_parquet() 返回 LazyFrame。之后的过滤、聚合和排序先形成逻辑计划，直到 collect() 才优化并执行。

3. 下推优化

谓词下推将 filter 移近数据源；投影下推只读取后续真正使用的列。两者都以“减少早期数据量”为目标。

同一个查询的两条执行路径

Eager 路径

读入全部列与全部行
在内存中物化 DataFrame
filter Volume ≥ 100
select 3 列 + group_by

Lazy 优化路径

查询图确认只需 3 列
扫描阶段应用 Volume 过滤
将较少的行交给 group_by
collect 返回最终结果
explain() 的用途不是预测精确耗时，而是确认优化器是否减少了扫描列、输入行和中间物化。
课堂演示：打印优化计划后再执行
import polars as pl

# scan_parquet 只登记数据源；下面的操作先组合成查询计划。
query = (
    # 指定 data_*.parquet，避免 macOS 外置盘的 ._ 辅助文件被当成数据。
    pl.scan_parquet("data/lake/**/data_*.parquet")
    # 过滤条件会尽量下推到扫描阶段，减少后续处理行数。
    .filter(pl.col("Volume") >= 100)
    .group_by("symbol")
    .agg(
        pl.len().alias("trades"),
        pl.col("Volume").sum().alias("volume"),
        (pl.col("Price") * pl.col("Volume") / 100)
            .sum().alias("amount_yuan"),
    )
    # 先按成交额降序排序，再只保留前 10 名。
    .sort("amount_yuan", descending=True)
    .head(10)
)

print(query.explain())  # 先看优化后的计划
result = query.collect() # 到这里才执行
print(result)

TOPIC 05 · CACHE

缓存是什么：结果副本、命中与失效

缓存先把一次费时计算的结果保存起来，下次条件完全相同时直接复用，避免重复查询和计算。

学习目标先能用自己的话说明“缓存是一份可以丢掉并重新计算的结果副本”；再区分缓存键、命中、未命中、LRU 和失效。
直观例子：第一次计算“2026-06-30 成交额最高的股票”时，DuckDB 要读 Parquet、分组、求和、排序。当前自编数据只有 8 只股票，缓存会把这 8 行结果暂存在内存里。再查完全相同的问题时，可直接返回这 8 行，不再执行 SQL。

缓存有什么好处

缓存保存的是“可以从原始数据重新算出来”的副本，用额外空间换取更少的重复计算。

重复查询更快

相同缓存键命中时，省去文件扫描、分组、排序等完整计算路径，只返回已经得到的结果。

减少磁盘与 CPU 压力

热点日期或热点参数被频繁访问时，底层 Parquet 和查询引擎不必反复承担同一工作。

延迟更稳定

命中缓存的请求不再依赖当时的磁盘状态和查询负载，响应时间通常比重新计算更可预测。

代价与适用边界：缓存会占用内存，最难的是失效。缓存键若没有包含数据版本，就可能很快地返回旧答案；结果本来就很便宜或几乎不重复时，缓存反而增加复杂度。

一句话定义缓存

缓存（cache）是为了下次更快而保留的结果副本。在本节代码中，真实数据源仍然是 Parquet，DuckDB 仍然是计算引擎，缓存只是 Python 进程内存里的一份“已算好答案”。

缓存键（key）

结果的身份证。本例是 (date, data_version)，例如 ('20260630', 'v1')。

缓存值（value）

这个键对应的已计算结果，即成交额排名前 10 的列表。

命中（hit）

键已经存在：直接取结果，不进入函数体，所以 SQL 不会再执行。

未命中（miss）

键不存在：正常执行 SQL，得到结果后再存一份。Miss 不是错误。

第一次调用 top_amount('20260630', 'v1')：内存里没有这个键 → miss → 执行 DuckDB 查询 → 保存结果。
第二次调用同样参数：键已存在 → hit → 直接返回结果，函数里的 SQL 不再运行。
第三次改成 v2：键变为 ('20260630', 'v2') → 对缓存来说是新问题 → miss → 重新查询。
调用查找的键结果是否执行 SQL
第 1 次 v1(20260630, v1)miss是
第 2 次 v1(20260630, v1)hit否
第 3 次 v2(20260630, v2)miss是

@lru_cache(maxsize=128) 又是什么

它是 Python 提供的函数缓存装饰器。可以把它理解为：在 top_amount 外面包一层自动字典，用所有函数参数组成键，用返回值作为值。maxsize=128 表示最多保留 128 个不同键；满了以后，LRU（Least Recently Used）优先淘汰最久没用的那一个。

缓存不是永久存储。 本例的 lru_cache 在 Python 进程退出后就消失；即使消失也没有丢失原始数据，只是下次需要重新计算。
知识讲解：缓存是一个带有身份和生命周期的结果副本identity · capacity · invalidation
1. 缓存键定义结果身份

查询日期、字段、过滤条件和数据版本中任意一项改变，都可能产生不同结果。这些维度应全部进入缓存键。

2. 命中与未命中

命中时直接复用结果；未命中时执行原始查询并写回缓存。冷查询和热查询的延迟应分开测量。

3. LRU 与失效

LRU 在容量满时淘汰最久未使用项，解决“存不下”。版本号、文件哈希或显式清理解决“结果已过期”。

一次查询的缓存路由
key = (date=20260630, fields, filters, data_version=v2)
查询请求标准化参数并生成键
→
HIT键存在：直接返回结果
MISS键不存在：查 DuckDB → 写缓存 → 返回
数据 v1key 含 v1
→
底层更新为 v2内容已变更
→
key 必须变为 v2否则可能返回过期的 v1
缓存正确性无法由命中率或延迟保证。只有当缓存键完整表达输入与数据版本时，“命中”才意味着可以复用的同一结果。

为什么键里还要放“数据版本”

假设 9:00 查询 20260630，得到结果 A，缓存键只是 20260630。10:00 时 Parquet 被更正，正确结果应变成 B。如果再查时仍只用日期当键，系统会命中旧结果 A：它很快，但是错的。

9:00 · 数据 v1key=(20260630,v1) → 结果 A
→
10:00 · 数据更正为 v2相同日期，底层内容已不同
→
key=(20260630,v2)新 key 未命中 → 重算得到 B

失效（invalidation）就是“不再使用已过时的缓存结果”。本节不是手工删除 A，而是让 v2 生成新键，自然不会命中 v1。

import duckdb

from functools import lru_cache
from hashlib import sha256
from pathlib import Path
from time import perf_counter
import duckdb

DATA_ROOT = Path("data/lake")

# 指纹只读取文件元数据，速度快；它不等同于逐字节内容哈希。
def data_fingerprint(root: Path) -> str:
    records = []
    for path in sorted(root.rglob("*.parquet")):
        stat = path.stat()
        # 相对路径、大小或修改时间任一变化，最终 SHA-256 都会变化。
        records.append(
            f"{path.relative_to(root)}|{stat.st_size}|{stat.st_mtime_ns}"
        )
    return sha256("\n".join(records).encode()).hexdigest()[:16]

@lru_cache(maxsize=128)
def cached_top_amount(date: str, fingerprint: str):
    # fingerprint 虽未出现在 SQL 中，但它是函数参数，因此进入缓存键。
    return duckdb.execute("""
        SELECT symbol, sum(Price * Volume) / 100 AS amount
        FROM read_parquet('data/lake/**/data_*.parquet', hive_partitioning=true)
        WHERE date = ? GROUP BY symbol
        ORDER BY amount DESC LIMIT 10
    """, [date]).fetchall()

# 同时显示耗时与 cache_info，区分“很快”和“确实命中缓存”。
def run(label, version):
    start = perf_counter()
    cached_top_amount("20260630", version)
    print(label, round((perf_counter() - start) * 1000, 3), "ms",
          cached_top_amount.cache_info())

version_1 = data_fingerprint(DATA_ROOT)

target = next(DATA_ROOT.rglob("*.parquet"))
target.touch()
version_2 = data_fingerprint(DATA_ROOT)
run("数据版本变化后", version_2)

# 通过断言把课堂观察变成可自动检查的结论。

当数据天然表示为“日期 × 股票 × 特征”或更高维张量时，Zarr 使用 NumPy 风格索引、Chunk 和 Shard 组织可局部读取的持久化数组。

学习目标理解数组形状、Chunk 与 Shard 的不同职责；能根据常见切片方向选择 Chunk 形状，并说明 Zarr 与 Parquet 各自适合的数据模型。
直观例子：本节只使用 4 天 × 6 只虚构股票 × 3 个因子，共 72 个自编数值。数组形状写作 (4, 6, 3)。例如 cube[0, 1, 0] = 0.02，明确表示“第 1 天、S002、momentum”的值。

Zarr 为什么要使用 Chunk

巨大数组若保存成一个不可分割的数据块，取一个坐标也可能需要读取整块。Chunk 把数组切成可独立定位、压缩和处理的最小逻辑块。

局部读取

只定位与切片相交的 Chunk。本例取 [0:2,0:3,:] 时覆盖 18 个值，而不是整个数组的 72 个值。

独立压缩与解压

每个 Chunk 单独编码；读取一个切片时，不必先把其他 Chunk 解压到内存，降低无关 I/O 和峰值工作内存。

便于并行处理

不同 Chunk 可以交给不同任务读取、计算或写入。数组足够大且存储系统允许并发时，可以利用多个核心或工作节点。

局部更新

修改少量坐标时，逻辑上只需定位受影响的 Chunk，而不必重写整个数组；若使用 Shard，物理重写范围还取决于存储实现。

Shard 控制对象数量

Chunk 很细会产生大量小对象。Zarr 3 可把多个 Chunk 装进一个 Shard，同时保留 Chunk 级索引。

def touched_chunk_ids(slices, chunk_shape):
    ranges = []
    for part, chunk_size in zip(slices, chunk_shape):
        first = part.start // chunk_size
        last = (part.stop - 1) // chunk_size
        ranges.append(range(first, last + 1))
    return list(product(*ranges))

TOPIC 07 · FREE-THREADED PYTHON

Free-threaded Python：没有 GIL 之后会发生什么

CPython 3.13 起提供可选的 Free-threaded 构建，使多个 Python 线程能够在不同 CPU 核心上同时执行 Python 字节码。

学习目标理解 GIL、操作系统线程和 CPU 核心的关系；能用运行时信息判断当前解释器是否支持 Free-threading，并用同一段 CPU 密集代码比较串行与线程池。
直观例子：有两项各需 40 ms 的纯 Python 计算。普通 CPython 即使开两个线程，某一时刻通常仍只有一个线程在执行 Python 字节码，总计算时间理想下限仍接近 80 ms；Free-threaded 解释器若有两颗空闲核心，理想情况下可让两项任务同时推进，接近 40 ms。

Free-threaded Python 可能带来什么好处

它最重要的变化是：多个线程有机会在不同 CPU 核心上同时执行 Python 字节码，而不再由一个进程级 GIL 把这部分工作串行化。

纯 Python CPU 任务可真并行

可拆成独立任务的循环、解析或计算，有机会同时使用多颗核心；普通 CPython 的线程通常只能轮流执行这些字节码。

线程共享内存更直接

线程可以共享同一组 Python 对象，不像多进程那样经常需要复制、序列化或通过进程间通信传递结果。

可继续使用线程接口

已有的 threading 和 ThreadPoolExecutor 模型仍然可用，CPU 并行不一定必须改写成多进程架构。

代价与适用边界：并行不是自动加速。线程同步、内存带宽、对象锁和任务粒度都会产生开销；共享状态更容易出现竞态，扩展库也必须确认兼容。I/O 等待在普通 CPython 中原本就能重叠，不需要为了 I/O 单独改用 Free-threaded 构建。

GIL 到底是什么

GIL 是 Global Interpreter Lock，中文常译为“全局解释器锁”。这里讨论的是最常用的 Python 实现 CPython。普通 CPython 在一个解释器进程内执行 Python 字节码前，线程需要先持有这把锁；因此同一时刻通常只有一个线程真正执行 Python 层代码。

进程 Process一个正在运行的 Python 程序，拥有自己的内存空间和一个 GIL。
线程 Thread进程中的执行路线；多个线程共享列表、字典等内存对象。
CPU 核心 Core真正执行机器指令的硬件；多核要同时有可运行任务才有价值。
Python 字节码CPython 解释器执行的中间指令；纯 Python 循环会持续执行大量字节码。
创建两个 OS 线程Thread A 与 B 都已经存在，也都可以被操作系统调度。
A 取得 GILA 执行一段 Python 字节码；B 即使位于另一核心也暂不能执行 Python 字节码。
锁发生交接A 遇到 I/O、主动释放或到达切换时机后，B 才有机会取得 GIL。
结果是并发而非并行A、B 都在推进，但纯 Python CPU 工作通常不是同一时刻在两核执行。
说法是否正确原因
“有 GIL 就不能创建线程”错误线程真实存在；限制的是同一解释器内同时执行 Python 字节码。
“有 GIL，I/O 线程也没用”错误磁盘、网络或 sleep 等等待期间通常会释放 GIL，其他线程可继续。
“GIL 会自动保护业务数据”错误检查库存和扣减库存是多步逻辑，线程仍可能在步骤之间交错，仍需 Lock。
“Free-threaded 一定线性加速”错误还受线程开销、内存带宽、任务粒度和扩展库兼容性影响。
知识讲解：GIL 从“全局串行门”变成可选机制GIL · OS threads · CPU cores · compatibility
1. CPU-bound：线程主要在做计算

例如 150 万轮纯 Python 整数运算。普通 CPython 的四个线程会轮流持有 GIL，因此总耗时通常与串行接近，甚至因切换稍慢。

2. I/O-bound：线程大部分时间在等待

例如四个任务各等待 0.12 秒。等待时线程不需要执行 Python 字节码并可释放 GIL，因此等待能够重叠，总时间可从约 0.48 秒降到约 0.12 秒。

3. Free-threaded：CPU 线程有机会真并行

关闭 GIL 后，多个线程可同时执行 Python 代码，但共享对象需要更细粒度的线程安全机制。部分不兼容扩展还可能在导入时重新启用 GIL。

def cpu_work(task):
    """纯 Python 整数循环：大部分时间都在执行 Python 字节码。"""
    value = int(task["seed"])
    checksum = 0
    for _ in range(int(task["rounds"])):
        value = (value * 1_664_525 + 1_013_904_223) & 0xFFFFFFFF
        checksum ^= value
    return checksum

    return result, perf_counter() - start

from concurrent.futures import ThreadPoolExecutor
from pathlib import Path
from threading import Barrier, Lock
import csv

with Path("data/orders.csv").open(encoding="utf-8") as file:
    orders = list(csv.DictReader(file))
initial_stock = int(orders[0]["initial_stock"])
quantities = [int(order["quantity"]) for order in orders]

# 错误版：两线程先后执行 Python 字节码，但“检查”和“扣减”不是同一步。
# Barrier 故意让两张订单都在库存仍为 10 时完成检查，再继续扣减。
stock = initial_stock
checked = Barrier(2)
def unsafe_buy(quantity):
    global stock
    if stock >= quantity:
        checked.wait()
        stock -= quantity
        return True
    return False

with ThreadPoolExecutor(max_workers=2) as pool:
    unsafe_results = list(pool.map(unsafe_buy, quantities))
print("unsafe:", unsafe_results, "final stock:", stock)

# 正确版：Lock 把“检查库存 + 扣减库存”包成不可交错的临界区。
stock = initial_stock
stock_lock = Lock()
def safe_buy(quantity):
    global stock
    with stock_lock:
        if stock >= quantity:
            stock -= quantity
            return True
        return False

with ThreadPoolExecutor(max_workers=2) as pool:
    safe_results = list(pool.map(safe_buy, quantities))
print("safe  :", safe_results, "final stock:", stock)

用同一份 12,000 行虚构成交数据，把前七个主题连接成一条可以完整运行、交叉验证和重复使用的数据流水线。

这一节不是再增加一个新工具它要回答的是：CSV、Parquet、分区、Polars、DuckDB、缓存、Zarr 和线程分别应当出现在完整程序的哪一步，以及前一步的输出怎样成为后一步的输入。
最终问题：给程序一个日期 20260630，找出当天成交额最高的 3 只虚构股票；再处理全部 6 天，把“每日 × 每只股票”的 VWAP 保存成可以按坐标切片的 Zarr 数组。Price 使用整数“分”，因此 VWAP 也以“分”为单位。

把这些技术串起来有什么好处

完整流水线的价值不在于工具数量，而在于每一步都有明确输入、输出和可核对结果。

每个工具只负责擅长的部分

Parquet 负责持久化，分区负责文件剪枝，Polars 和 DuckDB 负责分析，缓存负责复用，Zarr 负责数组切片。

中间结果可以单独检查

日期文件数、Top 3、缓存命中和 Zarr 坐标都能独立核对，出错时更容易定位到具体阶段。

同一口径可以交叉验证

Polars 与 DuckDB 独立计算同一个 Top 3；结果一致比只看到一份“看起来合理”的输出更可靠。

一次整理，多种使用方式

单日查询使用分区 Parquet，多日重复查询使用缓存，规则数组切片使用 Zarr，不必每次从 CSV 重新开始。

代价与适用边界：每增加一层都会增加代码、依赖和维护成本。真实项目应只保留能解决实际瓶颈的步骤，而不是为了“技术齐全”全部照搬。

输入、计算目标和最终产物

项目本例中的具体内容为什么需要它
源数据trades.csv：12,000 行，6 天，8 只虚构股票CSV 便于直接查看，但不作为反复分析时的最终存储格式。
单日结果每只股票的成交笔数、成交量、成交额和 VWAP回答“某天哪些股票成交额最高”。
交叉核对Polars 表达式和 DuckDB SQL 分别计算同一个 Top 3两条独立计算路径结果一致，可以发现字段、公式或过滤条件写错的问题。
批量产物Zarr 数组 shape=(6,8)，坐标为“日期 × 股票”后续可以快速取得某天全部股票或某只股票的 6 天 VWAP。
成交额 = Price × Volume　　VWAP = Σ(Price × Volume) ÷ ΣVolume

例如某股票只有两笔成交：10.00 元成交 100 股，10.20 元成交 300 股。简单平均价格是 10.10 元；VWAP 会考虑第二笔数量更大，所以是 (1000×100 + 1020×300) ÷ 400 = 1015 分，即 10.15 元。

同一份数据怎样贯穿七个主题建立存储 · 查询复用 · 批量产出

每个主题在代码里只承担一个明确职责

主题代码中的位置去掉以后会怎样
T1表示与压缩write_parquet(compression="zstd")只能反复解析体积更大、没有列类型和行组统计的 CSV。
T2文件布局PARTITION_BY (date)查一天时不能先从目录层跳过另外 5 天。
T3Polars Lazyscan_parquet → group_by → collect失去延迟执行和扫描阶段优化这条计算路径。
T4DuckDB SQL另一条 GROUP BY 查询缺少独立实现，公式写错时可能只得到一个“看起来合理”的结果。
T5缓存@lru_cache + 数据版本同一天、同一版本的汇总会被重复计算；只用日期作键又可能返回旧结果。
T6Zarrshape=(6,8)、chunks=(1,4)最终日汇总仍是零散表格，不能直接用二维坐标切片。
T7并发ThreadPoolExecutor6 个互不依赖的文件只能逐个调度；是否加速仍应以真实环境测量为准。
完整课堂演示：从 CSV 一直运行到 Zarr
from concurrent.futures import ThreadPoolExecutor
from functools import lru_cache
from pathlib import Path
import hashlib
import shutil

import duckdb
import numpy as np
import polars as pl
import zarr


SOURCE = Path("data/trades.csv")
WORK = Path("data/end-to-end")
PARQUET = WORK / "trades-zstd.parquet"
LAKE = WORK / "by-date"
ZARR_STORE = WORK / "daily-vwap.zarr"

# 每次从同一份虚构 CSV 重建结果，确保课堂上可以重复演示。
if WORK.exists():
    shutil.rmtree(WORK)
WORK.mkdir(parents=True)

# T1 · 数据表示：统一类型，再把文本 CSV 写成带统计信息的 ZSTD Parquet。
trades = pl.read_csv(SOURCE).with_columns(
    pl.col("date").cast(pl.String),
    pl.col("Price").cast(pl.Int32),
    pl.col("Volume").cast(pl.Int32),
    pl.col("BSFlag").cast(pl.Int8),
)
trades.write_parquet(PARQUET, compression="zstd", statistics=True)

# T2 + T4 · 文件布局与 SQL：DuckDB 把总文件拆成 6 个日期目录。
connection = duckdb.connect()
connection.execute(f"""
COPY (SELECT * FROM read_parquet('{PARQUET.as_posix()}'))
TO '{LAKE.as_posix()}'
(FORMAT parquet, PARTITION_BY (date), OVERWRITE);
""")
daily_files = sorted(LAKE.rglob("data_*.parquet"))
daily_file_by_date = {
    path.parent.name.removeprefix("date="): path.resolve()
    for path in daily_files
}
available_dates = sorted(daily_file_by_date)
available_symbols = sorted(trades["symbol"].unique().to_list())

# T5 · 缓存一致性：路径、大小和修改时间共同形成数据版本。
def lake_version():
    parts = []
    for path in daily_files:
        stat = path.stat()
        parts.append(f"{path.relative_to(LAKE)}:{stat.st_size}:{stat.st_mtime_ns}")
    return hashlib.sha256("|".join(parts).encode()).hexdigest()[:12]

# T3 · Polars Lazy：只有 collect() 才真正读取某一天的 Parquet。
@lru_cache(maxsize=32)
def cached_daily_summary(date_text, data_version):
    path = daily_file_by_date[date_text]
    return (
        pl.scan_parquet(path)
        .with_columns((pl.col("Price") * pl.col("Volume")).alias("turnover"))
        .group_by("symbol")
        .agg(
            pl.len().alias("trades"),
            pl.col("Volume").sum().alias("volume"),
            pl.col("turnover").sum(),
        )
        .with_columns((pl.col("turnover") / pl.col("volume")).round(2).alias("vwap"))
        .sort(["turnover", "symbol"], descending=[True, False])
        .collect()
    )

def daily_summary(date_text):
    # 数据文件变化时，lake_version 变化，自然形成一个新的缓存键。
    return cached_daily_summary(date_text, lake_version())

selected_date = "20260630"
selected_path = daily_file_by_date[selected_date]
polars_first = daily_summary(selected_date)   # 冷查询：miss
cache_after_first = cached_daily_summary.cache_info()
polars_second = daily_summary(selected_date)  # 相同日期和版本：hit
cache_after_second = cached_daily_summary.cache_info()

# T4 · DuckDB：独立用 SQL 计算同一结果，作为交叉核对。
duckdb_top3 = connection.execute("""
SELECT
    symbol,
    count(*) AS trades,
    sum(Volume) AS volume,
    sum(Price * Volume) AS turnover,
    round(sum(Price * Volume)::DOUBLE / sum(Volume), 2) AS vwap
FROM read_parquet(?)
GROUP BY symbol
ORDER BY turnover DESC, symbol
LIMIT 3
""", [str(selected_path)]).pl()

columns = ["symbol", "trades", "volume", "turnover", "vwap"]
polars_top3_rows = polars_second.select(columns).head(3).rows()
duckdb_top3_rows = duckdb_top3.select(columns).rows()

# T7 · 并发执行：六个互不依赖的日期文件可以并发读取和聚合。
with ThreadPoolExecutor(max_workers=4) as pool:
    summaries = dict(zip(available_dates, pool.map(daily_summary, available_dates)))

# T6 · Zarr：把各日各股票的 VWAP 变成“日期 × 股票”二维数组。
vwap_cube = np.empty((len(available_dates), len(available_symbols)), dtype="float32")
for date_index, date_text in enumerate(available_dates):
    values_by_symbol = dict(summaries[date_text].select("symbol", "vwap").iter_rows())
    for symbol_index, symbol in enumerate(available_symbols):
        vwap_cube[date_index, symbol_index] = values_by_symbol[symbol]

vwap_array = zarr.create_array(
    store=str(ZARR_STORE),
    shape=vwap_cube.shape,
    chunks=(1, 4),
    shards=(2, 8),
    dtype="float32",
    zarr_format=3,
)
vwap_array[:] = vwap_cube
vwap_array.attrs["dates"] = available_dates
vwap_array.attrs["symbols"] = available_symbols
reopened = zarr.open_array(str(ZARR_STORE), mode="r")

# 最终只打印课堂上需要核对的事实，避免用不稳定的耗时作结论。
print("输入:", trades.height, "行 /", len(available_dates), "天 /", len(available_symbols), "只股票")
print("Parquet:", round(PARQUET.stat().st_size / 1024, 1), "KiB / 日期文件:", len(daily_files), "个")
print("第一次查询:", cache_after_first)
print("第二次查询:", cache_after_second)
print("两次结果一致:", polars_first.equals(polars_second))
print("Polars 与 DuckDB Top 3 一致:", polars_top3_rows == duckdb_top3_rows)
print("20260630 按成交额 Top 3（价格单位：分）:")
for symbol, trade_count, volume, turnover, vwap in duckdb_top3_rows:
    print(f"  {symbol}: trades={trade_count}, volume={volume}, turnover={turnover}, vwap={vwap:.2f}")
print("并发汇总:", len(summaries), "天，每天", summaries[selected_date].height, "只股票")
print("Zarr shape/chunks/shards:", reopened.shape, reopened.chunks, reopened.shards)
date_index = available_dates.index(selected_date)
symbol_index = available_symbols.index("S002")
print("Zarr[20260630, S002] VWAP:", round(float(reopened[date_index, symbol_index]), 2))
print("最终缓存:", cached_daily_summary.cache_info())

assert np.allclose(reopened[:], vwap_cube)
assert polars_top3_rows == duckdb_top3_rows

按输出顺序理解发生了什么

先落盘：12,000 行 CSV 被写为 8.4 KiB 的 ZSTD Parquet，再拆成 6 个日期文件。文件很小是因为数据是为课堂编造的高度规律小样本，不能据此推断真实行情的压缩率。
定位一天：日期目录被整理成“日期 → 文件”的映射；选择 20260630 后只读取当天的 data_0.parquet。
计算并复用：第一次查询产生 1 次 miss；第二次使用相同日期和数据版本，hits 从 0 变成 1，结果没有重新聚合。
独立交叉核对：Polars 表达式和 DuckDB SQL 都得到 S008、S007、S006，说明 Top 3 的筛选、排序和 VWAP 公式一致。
扩展到全部日期：线程池调度 6 份日汇总；其中 20260630 已在缓存内，所以最终共有 6 个 miss、2 个 hit 和 6 份缓存结果。
变成数组：最终 Zarr 的 (6,8) 表示 6 个日期 × 8 只股票；[20260630, S002] 对应的 VWAP 是 1039.94 分。
贯穿全文的关键不是“把所有库都用一遍”。而是让每个工具只解决它擅长的问题，并在步骤之间留下可以核对的事实：文件数能数、两种查询能对比、缓存能统计、数组坐标能重新读取。
